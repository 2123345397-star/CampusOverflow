# 团队角色承诺书（TeamX）

> 团队：TeamX　项目：CampusOverflow 校园问答平台
> 版本：v1.0　日期：2026-10-26　适用：PO / SM / Developer / QA

本承诺书与《[团队章程 v1.0](charter-v1.0.md)》配套使用。每位成员按本学期承担的角色签署对应条款；角色轮换时重新签署，并在文末登记。

---

## 一、共同承诺（全员）

1. 按时参加实验、每日 12:30 站会、Sprint Planning、Review 与 Retro；确需缺席提前在群里请假，并补看会议纪要。
2. 对自己领取的任务负责；遇到阻塞按章程约定在 2 小时内在群里升级，不隐瞒、不拖延。
3. 遵守分支保护：不直接向 `main` push，所有改动走 `feature/<拼音>-<主题>` 分支 + PR。
4. 提交的代码可编译、可测试、有说明；不提交明文密码、密钥、`node_modules/`、构建产物。
5. 认真评审队友的 PR：24 小时内给出具体意见，评论 `LGTM` 前至少看过一遍改动。
6. 尊重不同意见，评审对事不对人；接受合理修改建议，有分歧用数据或原型说话。
7. 遵守学术诚信：引用外部代码注明来源，不抄袭、不篡改测试断言与提交记录。
8. 主动同步进度：看板卡片状态与真实情况一致，站会前更新完毕。

## 二、PO（产品负责人）· 魏志国

我承诺：

1. 维护 Product Backlog，按“价值 / 成本”排优先级，保证每个 Sprint 有明确、可验收的目标。
2. 为高优先级故事写清**验收标准**（优先使用 Gherkin 格式），避免“做完了但不符合预期”。
3. 需求来自真实用户访谈与课程要求，不凭个人喜好拍脑袋；新增需求先评估对当前 Sprint 的影响。
4. Sprint 中途控制范围变更；确需变更时与团队协商，替换等量任务并记录原因。
5. 每个 Sprint 结束前验收增量，给出“通过 / 不通过 + 原因”，不无限期拖延验收。
6. 不越权直接指挥技术实现；技术方案由团队讨论，PO 保留产品目标的最终解释权。

## 三、SM（Scrum Master）· 陈明哲、刘俊琒

我们承诺（双 SM 轮值主持）：

1. 守护流程：组织每日站会、Planning、Review、Retro，确保会议短而有效，有结论、有记录。
2. 维护看板与分支保护等协作设施，保证卡片状态真实、每人 `In Progress` 不超过 2 张。
3. 主动发现并清除障碍：跨人协调、环境问题、权限问题，2 小时内给出处理方案或升级。
4. 保护团队节奏：拒绝不合理的临时插入，必要时与 PO、教师沟通调整范围。
5. 主持 Retro，推动每个 Sprint 落地至少 1 条可验证的改进项，并在下次 Retro 复盘。
6. 不兼任 PO；不替成员写代码，但在关键任务无人认领时协调资源。
7. 维护仓库协作规范：PR 模板、分支命名、合并方式（Squash）与分支保护设置。

## 四、Developer · 青岑、房国栋

我们承诺：

1. 按章程的分支、提交、PR 规范工作；小步提交，单个 PR 尽量不超过 400 行。
2. 实现前先读验收标准与相关 ADR；有疑问先问清楚再动手，不自行扩大范围。
3. 新逻辑带单元测试；保持 `mvn test`、`npm run typecheck`、`npm run build` 通过。
4. 不修改既有测试断言来规避失败；确有问题在 PR 中说明并请教师确认。
5. 及时响应评审意见，逐条回复；合并后删除分支并更新看板。
6. 对自己负责的模块做基本自测，提交前在本地跑通，不把红的分支合并到 `main`。
7. 接口、错误码、架构有变更时，同步更新对应文档或 ADR。

---

## 五、QA · 青岑（兼 Developer）

我承诺：

1. 维护测试计划与缺陷清单，明确每个 Sprint 的回归范围。
2. Sprint 结束前完成一轮回归，输出“通过 / 阻塞项 / 风险”结论。
3. 发现缺陷先复现、再记录（环境、步骤、预期、实际），按严重程度分级。
4. 验收时对照 Gherkin 场景逐条检查，不以“页面能打开”代替验收。
5. 与 Developer 一起补充关键路径的自动化测试，避免同一缺陷回归两次。
